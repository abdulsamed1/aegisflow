# Product Brief — Appointment Automation Platform (v2)

> **الحالة:** نسخة أساسية مثبتة وجاهزة للانتقال إلى تخطيط السبرنتات.
> **آخر تحديث:** 2026-08-19
> **المرجع:** هذه نسخة محسّنة من مسودة مهندس مبتدئ، بعد فصل الحقائق المتحقق منها عن الافتراضات، وتثبيت القرارات المعلقة، وربط النطاق بحدود التكلفة المجانية الموثقة.

---

## 1. نظرة عامة على المنتج

منصة SaaS لأتمتة حجز مواعيد **الإقامة الدراسية في النمسا** عبر نظام المواعيد الرسمي [appointment.bmeia.gv.at](https://appointment.bmeia.gv.at/)، مع تركيز المرحلة الأولى على السفارة النمساوية في القاهرة.

يجمع المشغل بيانات كل عميل مرة واحدة، ثم تعمل المنصة تلقائيًا خلال نافذة التشغيل: تبحث عن موعد متاح، تطابق النتيجة مع قواعد العميل، وتكمل الحجز **آليًا حتى Submit**، ثم تسجل النتيجة وتنبه المشغل.

> **التموضع:** تبقى رؤية "Appointment Automation Platform" (BMEIA كأول integration) **رؤية فقط**. لا يُبنى في الـMVP أي طبقة تكامل عامة أو عزل متعدد البوابات — ذلك من مرحلة لاحقة.

---

## 2. الهدف التجاري

تحويل حجز المواعيد اليدوي إلى خدمة مؤتمتة تُشغَّل لعملاء متعددين، بأولوية قصوى للسرعة في الإمساك بالموعد عند ظهوره (المنافسة عالية)، وبأقل تكلفة تشغيل ممكنة.

**الأهداف القابلة للقياس:**

- إدخال بيانات العميل مرة واحدة وإعادة استخدامها في كل المحاولات.
- اكتشاف الموعد المطابق وحجزه أسرع من أي محاولة يدوية (يُقاس زمن slot-appearance → submit).
- منع الحجز المزدوج لنفس العميل بشكل مضمون.
- تسجيل كل محاولة وكل فشل مع رمز خطأ قابل للتصفية.
- تشغيل أولي بتكلفة $0 ضمن خطة Cloudflare المجانية.

## 3. المستخدمون

### Primary — مشغل الخدمة (المستخدم الوحيد في الـMVP)

- إنشاء وتعديل العملاء ومراجعة بياناتهم.
- تفعيل/إيقاف/إلغاء طلبات الحجز.
- ضبط تفضيلات الموعد لكل عميل.
- متابعة الحالة وآخر فحص وعدد المحاولات.
- استلام إشعارات Telegram عند الحجز أو الفشل الحرج.
- استلام بيانات الموعد ومرجع التأكيد عند النجاح.

### Secondary — العميل (طرف بيانات فقط)

يقدم بياناته مسبقًا. **لا يملك حسابًا ولا بوابة ولا إشعارات مباشرة في الـMVP** — التواصل معه يظل خارج المنصة.

## 5. نطاق الـMVP

### داخل النطاق

- دخول المشغل (مشغل واحد؛ يُقترح Cloudflare Access — مقترح يُحسم في الـPRD).
- CRUD للعملاء مع نموذج بيانات كامل: شخصي + جواز سفر + دراسة + إقامة + تفضيلات الموعد.
- تحقق بنيوي من البيانات قبل التفعيل (VALIDATION_ERROR يمنع التفعيل).
- دورة حياة وظيفة الحجز (آلة الحالات في القسم 9).
- جدولة تلقائية داخل النافذة مع عدالة توزيع المحاولات (القسم 10).
- قفل موزع لكل وظيفة عبر Durable Object.
- أتمتة Playwright: كشف التوافر ← مطابقة القواعد ← تعبئة البيانات ← مراجعة ← Submit ← التقاط التأكيد.
- وضع Dry-Run إلزامي يوقف التنفيذ قبل Submit حتى اجتياز بوابة G0 (القسم 20).
- تسجيل النتيجة: مرجع التأكيد + لقطة شاشة بصيغة يقررها مواصفات G0.
- سجل أحداث كامل في قاعدة البيانات.
- إشعارات Telegram: نجاح الحجز + الأعطال الحرجة.
- لوحة تحكم: جدول العملاء، الحالات، آخر فحص، عدد المحاولات، عرض السجلات.
- تشفير بيانات PII في التخزين + سياسة احتفاظ افتراضية (القسم 13).

### خارج النطاق (مع السبب)

- **بوابة عميل وإشعارات للعميل** — المشغل هو المستخدم الوحيد في الـMVP.
- **مدفوعات/فوترة** — لا يوجد تحصيل في هذه المرحلة.
- **إشعارات WhatsApp وEmail** — D4: Telegram فقط.
- **تكامل سفرات/أنظمة أخرى، Multi-tenant، White-label، API عام** — رؤية مرحلة 3 فقط.
- **ذكاء توقيت المواعيد كنظام تعلّم** — الـMVP يسجل الأحداث ويعرض إحصاءات فقط (القسم 18).
- **استرداد تلقائي من الأعطال** — يكتفي الـMVP بسياسة retry/backoff صريحة.

## 7. غير متحقق منه بعد — يتتبع في مواصفات البوابة

كل ما يلي **ممنوع افتراضه** ولا يُكتب أي selector أو endpoint أو معامل قبله. راجع `docs/portal-automation-spec.md` (بوابة G0، القسم 11) لحالة كل بند — فقد تحقق يوم 2026-08-19 جزء كبير (عقد الفحص، المعرفات، الجلسة) وبقي المعلق:

- بنية شبكة الأسبوع **عند وجود مواعيد فعلية** وتمثيل اليوم/الموعد القابل للنقر.
- مسار الحجز الكامل: نموذج بيانات العميل بحقوله وأنواعه وقواعد التحقق الإلزامية.
- موقع الـCAPTCHA الفعلي (BotDetect محمّل في الصفحات لكن لم يُرصد حقل أثناء الفحص).
- صيغة تأكيد الحجز (مرجع؟ صفحة نجاح؟ PDF؟) وسلوك اختفاء الموعد أثناء التعبئة.
- حدود المستقبل المقبولة لقيمة `Monday`.
- **شروط استخدام البوابة وسياسة الأتمتة/البوتات** — قرار المشغل المكتوب (البوابة لا تعرض أي ToS).
- سلوك الحماية من الروبوتات وحدود معدل الطلبات عند الاستخدام المكثف.

## 8. سير العمل الأساسي

```text
مشغل: إنشاء عميل → تعبئة البيانات → مراجعة وتحقق → تفعيل الوظيفة
   │
   ▼
Scheduler (كل دقيقة، يعمل 24/7)
   │  مفعل؟ غير محجوز؟ لا قفل؟ لا backoff معلق؟ ميزانية متصفح متبقية؟
   ▼
جلسة متصفح → فحص التوافر (كل أسابيع نافذة قواعد العميل)
   ├── لا موعد → تسجيل + backoff → إعادة
   ├── موعد غير مطابق للقواعد → تسجيل RULE_MISMATCH → إعادة
   └── موعد مطابق
           ▼
       قفل الوظيفة (DO)
           ▼
       تعبئة البيانات → مراجعة
           ▼
       [Dry-Run؟ توقف هنا مع تسجيل النتيجة]
           │
           ▼
       Submit
           ▼
       التقاط التأكيد (مرجع + لقطة)
           ▼
       BOOKED → إشعار Telegram → إيقاف دائم لكل محاولات هذا العميل
```

## 9. آلة الحالات الموحدة

النسخة السابقة عرّفت قائمتين متضاربتين (قسمي Job States وClient Status). هنا آلة واحدة لكل وظيفة، وحالة العرض للمشغل مشتقة منها.

| الحالة | المعنى | الانتقالات المسموحة | من يغيّرها |
|--------|--------|---------------------|-----------|
| DRAFT | بيانات ناقصة | → READY أو VALIDATION_ERROR أو CANCELLED | المشغل |
| VALIDATION_ERROR | فشل التحقق البنيوي للبيانات عند التفعيل | → DRAFT (بعد التصحيح) | النظام/المشغل |
| READY | بيانات مكتملة وغير مفعلة | → ACTIVE أو CANCELLED | المشغل |
| ACTIVE | مفعلة وتنتظر دورة الجدولة | → SEARCHING أو CANCELLED | المشغل/النظام |
| SEARCHING | محاولة فحص جارية | → ACTIVE (لا نتيجة) أو BOOKING | النظام |
| BOOKING | موعد مطابق، حجز جارٍ تحت القفل | → BOOKED أو BOOKING_FAILED | النظام |
| BOOKED | **نهائية** — حجز مؤكد ومسجل | لا انتقال | النظام |
| BOOKING_FAILED | فشل الحجز مع error_code | → ACTIVE (وفق backoff) أو CANCELLED | النظام/المشغل |
| TEMPORARY_ERROR | عطل عابر (بوابة/شبكة/متصفح) | → ACTIVE وفق backoff | النظام |
| PORTAL_ERROR | صفحة غير متوقعة/سلوك غير معروف | → ACTIVE مع تنبيه بعد تكرار الحد | النظام |
| CANCELLED | **نهائية** — إيقاف يدوي | لا انتقال | المشغل |
| EXPIRED | **نهائية** — تجاوز آخر تاريخ مقبول | لا انتقال | النظام |

**قاعدة الإيقاف المؤقت:** "Paused" ليست حالة بل علامة `enabled=false` على وظيفة ACTIVE — يزيل هذا تكرار الحالة الغامض في النسخة السابقة.

**حارس الحجز المزدوج:** لا توجد أي مسارات تعيد وظيفة BOOKED إلى العمل، وقفل DO يمنع تنفيذين متوازيين لنفس الوظيفة.

## 10. الجدولة والعدالة

- **الفحص يعمل 24/7** (قرار D5): لا توجد نافذة زمنية — كل دقيقة يُعالج حتى 3 وظائف بترتيب العدالة، ويُفحص كل أسبوع داخل نطاق تواريخ قواعد العميل. الإيقاف الوحيد هو قاطع الميزانية وحدود معدل الطلبات.
- ترتيب المحاولات لكل دورة: **الأقدم في `last_check` أولًا** — العدالة تقيس الحمل القائم المتبقي، لا عدد المحاولات التي جرت اليوم (درس إنتاجي من سجلاتنا: قياس التدفق لا الرصيد يظلم صاحب الأقدمية).
- قيود متزامنة من الحد المجاني: 3 متصفحات كحد أقصى، ومتصفح جديد كل 20 ثانية — تُدار بمُخنق مركزي قبل أي تشغيل.
- **ميزانية المتصفح اليومية:** 600 ثانية/يوم (مجاني). بعد قياس G0 الفعلي (فحص ≈ 0.3–0.8 ثانية، متوسط ~270ms) تسع الميزانية نظريًا ~750–2000 فحص/يوم؛ القيد العملي الحقيقي هو 3 متصفحات متزامنة وحدود معدل الطلبات، لا الميزانية. مع ≤10 عملاء يبقى فحص متكرر لكل عميل داخل الحد المجاني. المُخنق يتوقف **قبل** 90% من الميزانية وينبه المشغل.
- إعادة المحاولة: `Failure ≠ Retry immediately` — backoff أسي (2، 4، 8… دقيقة، سقف 60 دقيقة) يُعاد تصفيره بعد نجاح أي فحص.
- التحقق التمييزي المطلوب في اختبارات الجدولة: عميل بـ`last_check` قديم و5 محاولات سابقة يجب أن يُختار قبل عميل بـ`last_check` حديث وصفر محاولات (اختبار يميز التصميم الجديد عن القديم).

## 11. قواعد المواعيد (Rules)

بيانات لكل عميل، تُخزن كصف في قاعدة البيانات:

```text
appointment_type = Student
date: >= 2026-09-01 AND <= 2026-10-31
time: 08:00 - 15:00
```

- النظام **لا يحجز** أي موعد لا يطابق قواعد العميل.
- المطابقة دالة نقية بدون آثار جانبية → تُختبَر كاختبار وحدة مباشرة على المصدر الحقيقي، بلا نسخة مكررة في ملفات الاختبار (درس إنتاجي).

## 12. الأتمتة والبوابة

المراحل (موثقة جزئيًا في `portal-automation-spec.md`):

```text
Discovery (موثق G0): POST /HomeWeb/Scheduler → تحليل عقد الرسالة
Booking (UNVERIFIED حتى أول موعد): Select Slot → Fill Data → Review → Submit → Capture Confirmation
```

- الفحص لا يحتاج مشي المعالج: طلب POST واحد يكفي، وجلسة واحدة تخدم فحوصات متعددة؛ `browser.close()` داخل `try/finally` دائمًا — الجلسات المنسية تستهلك الميزانية حتى مهلة الخمول (موثق في إرشادات Cloudflare).
- إعادة استخدام حالة الجلسة عبر KV وفق مثال Cloudflare الرسمي (storageState).
- **Dry-Run إلزامي:** أي بناء أتمتة يشمل وضعًا يوقف التنفيذ قبل Submit ويصور النتيجة فقط. لا يُرفع Dry-Run إلا بعد G0 ومراجعة يدوية لنتيجته.
- الفصل بين Discovery وBooking يبقى كما في النسخة السابقة: خطأ في الاكتشاف لا يؤدي أبدًا إلى Submit.

## 13. الأمان والخصوصية

- تشفير PII (جواز السفر، بيانات الاتصال) على مستوى التطبيق قبل الكتابة في D1؛ المفتاح في Cloudflare Secrets — **ممنوع** أي سر أو بيانات عميل في الكود أو الإعدادات (قاعدة البيئة المعتمدة في AGENTS.md).
- حجب أرقام الجوازات من كل السجلات بقاعدة masking في المُسجِّل المركزي.
- مصادقة المشغل: مقترح Cloudflare Access (مجاني حتى 50 مستخدمًا) — يُحسم في الـPRD، والخيار البديل جلسات على الـWorker.
- فصل كامل بين اعتمادات المنصة وبيانات العملاء.
- **سياسة الاحتفاظ الافتراضية في الـMVP:** حذف بيانات العميل الشخصية بعد 30 يومًا من وصول الوظيفة لحالة نهائية (BOOKED/CANCELLED/EXPIRED)، أو فورًا بطلب المشغل. قابل للتعديل عند الحاجة.
- تسجيل الوصول والتعديل ضمن سجل الأحداث.

```text
              ┌────────────┘      │       └─────────────┐
              ▼                   ▼                     ▼
        ┌──────────┐      ┌─────────────┐      ┌──────────────┐
        │    D1    │      │ DO لكل وظيفة │      │  KV (جلسات)  │
        │ عملاء/وظائف│      │ قفل + حالة   │      │              │
        │ سجل أحداث │      │ (SQLite)     │      │              │
        └──────────┘      └─────────────┘      └──────────────┘
```

**مبدأ البساطة:** Worker واحد يجمع HTTP + الجدولة + ربط المتصفح. إذا اصطدم التنفيذ بحدود wall-clock في بيئة الإنتاج، يُفصل عامل متصفح مستقل ويُربط بـ Service Binding (بلا تكلفة طلبات إضافية — موثق). لا يُبنى هذا الفصل مسبقًا.

| المكوّن | الاختيار | التوافق مع الخطة المجانية |
|---------|----------|---------------------------|
| الحساب | Workers Free (D3: ترقية $5 عند الحاجة) | نعم |
| قاعدة البيانات | Cloudflare D1 | نعم |
| القفل والحالة الجارية | Durable Objects (SQLite-backed) | نعم (SQLite فقط في المجاني) |
| الجلسات | Workers KV (storageState) | نعم |
| الأتمتة | `@cloudflare/playwright` + Browser Run | نعم (بحدود القسم 6) |
| الجدولة | Cron Triggers | نعم |
| الإشعارات | Telegram Bot API (token في Secret) | مجاني |

## 15. معالجة الفشل

| الفشل | السلوك | ظاهر للمشغل؟ |
|-------|--------|---------------|
| بوابة غير متاحة / timeout | TEMPORARY_ERROR + backoff أسي | في السجل دائمًا؛ تنبيه عند تجاوز حد التكرار |
| انهيار متصفح / انتهاء جلسة | إعادة تشغيل جلسة واحدة، ثم backoff | في السجل |
| صفحة غير متوقعة | PORTAL_ERROR + لقطة DOM في السجل | في السجل؛ تنبيه بعد التكرار |
| الموعد اختفى أثناء الحجز | BOOKING_FAILED → ACTIVE وفق backoff | في السجل |
| رفض الحجز | BOOKING_FAILED + لقطة الصفحة للمراجعة اليدوية | تنبيه فوري |
| تنفيذ مزدوج | ممنوع بقفل DO + حارس BOOKED | اختبار تكامل إلزامي |
| 429 من Browser Run | احترام `Retry-After` | في السجل |
| استنزاف الميزانية اليومية | توقف نظيف عند 90% + تنبيه | تنبيه Telegram |

**مسارات الفشل الصامت:** كل مسار أعلاه يكتب سطرًا في سجل الأحداث أو يرسل تنبيهًا — لا يوجد مسار يفشل بلا أثر. الفجوة الحرجة الوحيدة المتبقية قبل البناء هي بوابة G0 نفسها (بلاها لا يوجد أتمتة أصلًا).

## 18. ذكاء توقيت المواعيد (نطاق MVP)

- تسجيل لكل فحص: الوقت والنتيجة (متاح/غير متاح) والمكتب والتصنيف.
- عرض إحصاءات بسيطة في اللوحة: الفحوصات لكل ساعة ونسبة الإصابة لكل ساعة.
- **خارج الـMVP:** أي توجيه تلقائي لجدول المحاولات بناءً على هذه البيانات (مرحلة 2).

---

## 19. معايير القبول (Definition of Done للـMVP)

1. مشغل واحد يسجل دخوله وينشئ عميلًا بالبيانات الكاملة ويفعّل وظيفة.
2. الجدولة تعمل تلقائيًا 24/7 وتفحص أسابيع نافذة قواعد العميل فقط (اختبار نطاق الأسابيع يميز التصميم).
3. فحص يكتشف موعدًا مطابقًا للقواعد في وضع Dry-Run ويسجل النتيجة بلا Submit.
4. لا يحدث أي Submit قبل إغلاق بوابة G0 ورفع Dry-Run بشكل صريح.
5. محاولتان متوازيتان لنفس العميل لا تنتجان حجزًا مزدوجًا (اختبار تكامل يميز السلوك الصحيح).
6. بعد BOOKED: إشعار Telegram خلال دقيقة، وتوقف دائم لكل الفحوصات على هذا العميل.
7. كل فشل يُسجل بـ`error_code` وتُعاد المحاولة وفق backoff.
8. لا يوجد أي سر أو بيانات عميل في الكود أو اللوجات (فحص آلي).
9. اللوحة تعرض الحالة وآخر فحص وعدد المحاولات لكل عميل، مع عرض السجلات.
10. ميزانية المتصفح اليومية تُراقب وتتوقف عند 90% مع تنبيه.

## 20. بوابة G0 — مواصفات أتمتة البوابة (شرط مسبق إلزامي)

**الحالة: منجزة جزئيًا.** المواصفات موجودة في `docs/portal-automation-spec.md` ومثبتة بجلسات متصفح حقيقية (2026-08-19): عقد الفحص، معرفات التصنيفات، سلوك الجلسة، القياسات. **ما يبقيها مفتوحة:** (1) رصد أول موعد وتوثيق مسار الحجز، (2) القرار القانوني المكتوب من المشغل بشأن الأتمتة. حتى إغلاقهما يبقى Dry-Run مفروضًا — **لا يبدأ أي سبرنت حجز فعلي قبل الإغلاق.**

محتوياتها (متحقق منها فقط):

- URL البوابة وسلوك الدخول/الجلسة/الـtimeout (موثق بجلسة متصفح حقيقية).
- اختيار المكتب والتصنيف، وحقول النموذج وأنواعها والحقول الإلزامية وقواعد التحقق.
- تمثيل التقويم والتوافر، وصيغة تأكيد الحجز (مرجع/صفحة/PDF).
- **مراجعة شروط الاستخدام وسياسة البوتات — قرار قبول/رفض صريح ومكتوب.**
- قياس زمن الفحص الفعلي لإعادة معايرة ميزانية القسم 10.
- حزام Dry-Run قابل للتشغيل يدويًا على بيئة حقيقية.
