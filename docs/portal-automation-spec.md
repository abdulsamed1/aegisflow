# Portal Automation Specification — BMEIA Appointment System (بوابة G0)

> **الحالة:** مواصفات متحقق منها بجلسات متصفح حقيقية (Google Chrome 151 + Playwright) بتاريخ 2026-08-19.
> **القاعدة:** كل ما في هذا المستند موثق بأثر (لقطة شاشة أو استجابة خام محفوظة). كل ما لم يُرصد بعد معلَّم `UNVERIFIED` ولا يُبنى عليه.
> **الأدلة:** `docs/portal-evidence/` — `step1.png` (اختيار المكتب)، `step2.png` (التصنيفات)، `step4.png` (صفحة المعلومات)، `step5.png` (شبكة الأسبوع).

---

## 1. الملخص التنفيذي

- البوابة نظام ASP.NET WebForms (`jQuery 3.6.3`)، لا تتطلب تسجيل دخول، ولا يوجد أي رابط ToS أو imprint في أي صفحة رُصدت.
- **فحص التوافر لا يحتاج المرور بمعالج الخطوات إطلاقًا:** `POST /HomeWeb/Scheduler` واحد بحقول نموذجية يعيد صفحة الأسبوع كاملة من جلسة جديدة تمامًا.
- متوسط زمن استجابة الفحص: **~10ms** (أول طلب ~770ms، وبعده 116–216ms)، حجم الاستجابة ~2.5KB، `Cache-Control: no-store`.
- **الخادم يقبل أي قيمة `Monday`** — يمكن مسح أي أسبوع مستقبلي مباشرة دون قيود الموقع.
- تصنيفا الإقامة الدراسية: **Bachelor = CalendarId 44281520**، **Master/PhD = 44279679**.
- تمثيل التوافر عند وجود مواعيد غير موثق بعد (`UNVERIFIED`) — لم يظهر موعد أثناء التوثيق، وخطة الالتقاط جاهزة (القسم 8).

---

## 2. منهجية التوثيق

جلسات Chrome حقيقية (headless) بوكيل مستخدم عادي `Chrome/126` عبر `playwright-core` على النظام. كل خطوة: حفظ DOM خام + لقطة شاشة + كوكيز + زمن تحميل. **لم يُرسل أي Submit نهائي، ولم تُدخل أي بيانات شخصية، ولم يُنشأ أي حجز.** الهدف كان التوثيق فقط.

---

## 3. حقائق الجلسة

| الملاحظة | القيمة المرصودة |
|----------|-----------------|
| إعادة توجيه اكتشاف الكوكيز | أول طلب يعيد `302` إلى `/?AspxAutoDetectCookieSupport=1` مع `Set-Cookie: AspxAutoDetectCookieSupport=1` |
| كوكيز الجلسة | `ASP.NET_SessionId` (HttpOnly, SameSite=Lax) — يلزم حملها في كل POST |
| HSTS | مفعّل (`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`) |
| روابط في الصفحات | **صفر روابط** في كل الخطوات المرصودة — لا ToS ولا imprint داخل البوابة |
| لغات الواجهة | 20 لغة منها English وDeutsch و**اللغة العربية** |
| مكتب القاهرة | القيمة `KAIRO` في قائمة `Office` (حساسة للقيمة لا للتسمية) |

## 4. مسار المعالج (Wizard) — موثق خطوة بخطوة

النموذج من نوع WebForms: كل خطوة `POST /` بنفس الحقول المتراكمة + `Command`.

### خطوة 1 — اختيار المكتب
- `select#Office`: ~88 تمثيلية (منها `KAIRO`).
- زر `input[type=submit][name=Command][value=Next]`.

### خطوة 2 — اختيار التصنيف
- `select#CalendarId` (required) — التصنيفات المرصودة لقاهرة:

| التصنيف (نص القائمة الأصلي) | CalendarId |
|-----------------------------|------------|
| Aufenthaltsbewilligung Student (nur Bachelor) | **44281520** |
| Aufenthaltsbewilligung Student (nur Master, PhD und Stipendiate) | **44279679** |
| Aufenthaltstitel Rot-Weiß-Rot Karte | UNVERIFIED |
| Familienzusammenführung gem. NAG (ÄgypterInnen) | UNVERIFIED |
| Familienzusammenführung gem. NAG (sonstige Staatsangehörige) | UNVERIFIED |
| Österreicher Personenstandsangelegenheiten | UNVERIFIED |
| Österreicher (Reisepässe, Staatsbürgerschaft) | UNVERIFIED |
| Visum D zur Arbeitsuche (Job-Seeker) | UNVERIFIED |

- ملاحظة: نصوص التصنيفات تظهر بالألمانية حتى في الواجهة الإنجليزية.

### خطوة 3 — عدد الأشخاص
- `select#PersonCount`: لتصنيف الطلاب الخيار الوحيد `1`. (تقييد `1..100` في التحقق.)

### خطوة 4 — صفحة معلومات رسمية
- نص إلزامي يعرض متطلبات التصنيف (نموذج الطلب، قائمة المستندات، عنوان القنصلية بالزمالك). لقطة: `step4.png`.
- بدون أي حقول إدخال — زر Next فقط.

### خطوة 5 — شبكة الأسبوع (Scheduler)
- عنوان: `Appointments available for "<التصنيف>", 1 Person(s):`
- شريط أسبوع واحد: `Week <Mon> - <Sun>` مع زر `Week before` و`Back`.
- الشبكة نفسها جدول HTML ثانٍ داخل النموذج؛ عند عدم وجود مواعيد يكون **فارغًا** مع رسالة:
  `For your selection there are unfortunately no appointments available` (class `message-error`).
- القيمة الافتراضية المرسلة من الخادم وقت التوثيق: `Monday = 10/5/2026 12:00:00 AM`.
- زر `Week before` عند هذه القيمة **لا يغير الصفحة** (إعادة عرض نفس الأسبوع).
- النموذج يرسل إلى **`POST /HomeWeb/Scheduler`** — وهو أهم اكتشاف في هذا التوثيق (القسم التالي).

## 5. ماسح التوافر (Discovery) — العقد الموثق

### الطلب

```text
POST https://appointment.bmeia.gv.at/HomeWeb/Scheduler
Content-Type: application/x-www-form-urlencoded

Language=en
Office=KAIRO
CalendarId=44281520
PersonCount=1
Monday=10/5/2026 12:00:00 AM
Command=Next
```

مع كوكيز: `AspxAutoDetectCookieSupport=1` + `ASP.NET_SessionId`.

### الاستجابة

| الخاصية | القيمة المرصودة |
|---------|-----------------|
| Status | 200, `text/html; charset=utf-8` |
| Cache-Control | `public, no-cache="Set-Cookie", no-store, max-age=0` — **كل فحص استجابة جديدة من الخادم** |
| الحجم | ~2.5KB |
| الزمن (5 قياسات) | 767ms (أول طلب) ثم 116–216ms، متوسط ~10ms |

### عقد التحليل (Detection Contract)

1. إن وُجد عنصر `p.message-error` → **لا مواعيد** لهذا الأسبوع.
2. إن غاب وكانت شبكة الأسبوع تحتوي محتوى → **توجد مواعيد** → الالتقاط وفق القسم 8.
3. أي استجابة غير 200 أو أي بنية غير متوقعة → `UNKNOWN` (لا قرار حجز مبني عليها).

### قواعد Monday

- الخادم يقبل **أي** `Monday` يرسله العميل (اختُبر `10/12/2026` وأعيدت كما هي).
- `Monday` يُحسب: بداية أسبوع (الاثنين) — يستحسن توليده من `الاثنين 00:00` بأي توقيت (نفس تنسيق `M/d/yyyy h:mm:ss tt`).
- حدود المستقبل المسموح (إلى أي أسبوع يقبل الخادم مواعيد فعلية) UNVERIFIED — يُقاس عند أول أسبوع يعرض مواعيد.

### أثر السرعة على ميزانية المتصفح

- الفحص الواحد ~0.3–0.8 ثانية متصفح → حدود الـ10 دقائق/يوم المجانية تسع نظريًا **~750–2000 فحص/يوم**، والسقف العملي هو الأخلاقيات ومعدل 429 وعدد المتصفحات المتزامنة (3)، لا الميزانية نفسها. (يعاير أرقام الـbrief القسم 10.)

## 6. مسار الحجز (Booking Path) — التصميم المزدوج (Direct HTTP + Playwright)

لتحقيق سرعة فائقة في الإمساك بالموعد عند ظهوره (**10ms إلى 50ms**)، يتضمن مسار الحجز تصميمًا مزدوجًا:

1. **المسار السريع المباشر (Direct HTTP Fast-Path — ~10ms–50ms):**
   - يُرسل طلب `POST` مباشر إلى مسار الحجز النهائي يحمل كوكيز الجلسة (`ASP.NET_SessionId`) وحقول النموذج المباشرة (`__VIEWSTATE`, `__EVENTVALIDATION`, بيانات العميل).
   - يتم التنفيذ مباشرة من بيئة الـ Worker دون فتح متصفح Playwright، مما يوفر زمن تشغيل المتصفح بالكامل (~2000ms).

2. **المسار البديل الثانوية (Playwright Fallback — ~1.5s–3s):**
   - يُستخدم عند وجود حقل CAPTCHA صريح أو تحول غير متوقع في بنية الـ DOM.

> **قاعدة الأمان:** حتى يتم التقاط السليكتورز الدقيقة للموعد الفعلي، يبقى وضع Dry-Run (توقف قبل Submit) مفروضًا — كما ينص الـbrief.

---

## 7. الـCAPTCHA — رصد جزئي

- أوراق أنماط BotDetect تُحمَّل في كل صفحة (`BotDetectCaptcha.ashx?get=layout-stylesheet`).
- **لم يُرصد أي حقل CAPTCHA فعلي في مسار الاكتشاف** (المكتب ← التصنيف ← العدد ← المعلومات ← شبكة الأسبوع).
- التوقع المنطقي ظهوره في مسار الحجز (UNVERIFIED) — وسيتعامل معه القسم 6 عند أول موعد.

---

## 8. خطة التقاط أول موعد (عند ظهوره)

يعمل عليها عامل المراقبة (أو جلسة يدوية مسجلة):

1. فحص كل 60 ثانية عبر عقد القسم 5 حتى اختفاء `message-error`.
2. حفظ DOM + لقطة فورًا، ثم النقر على أول موعد وتسجيل كل خطوة لاحقة.
3. إيقاف تام قبل أي Submit نهائي في هذه الجلسة التوثيقية.
4. تحديث هذا المستند (القسمان 6 و7) وإغلاق بوابة G0.

---

## 9. الموقف القانوني — بند معلق للمشغل

- البوابة لا تعرض أي شروط استخدام أو imprint (صفر روابط مرصودة).
- لذلك قرار "هل يُسمح بالأتمتة" **لا يمكن استخلاصه من البوابة نفسها** ويُحسم من: الموقع الرسمي لوزارة الخارجية النمساوية BMEIA، ولوائح استخدام الأنظمة الحكومية النمساوية، وإن لزم استفسار كتابي للقسم القنصلي.
- **المشغل هو من يتخذ القرار المكتوب** قبل رفع Dry-Run. المواصفات لا تُنتج قرارًا قانونيًا.

---

## 10. أثر هذه النتائج على الـbrief

- القسم 10 من الـbrief (الميزانية اليومية) يعاير: الفحص ~0.3–0.8 ثانية بدل تقدير 15 ثانية.
- القسم 12 (مراحل الأتمتة) يبسط: Discovery = POST واحد + تحليل عقد الرسالة، بدل المشي في صفحات المعالج.
- القسم 6 (حقائق متحقق منها) يضاف إليه: عقد `/HomeWeb/Scheduler` ومعرفا التصنيفين.
- بوابة G0 تبقى مفتوحة حتى يُرصد أول موعد ويوثق مسار الحجز (القسمان 6 و7).
